# Contributing to Puma

By participating in this project, you agree to follow the [code of conduct].

[code of conduct]: https://github.com/puma/puma/blob/main/CODE_OF_CONDUCT.md

There are lots of ways to contribute to Puma. Some examples include:

* creating a [bug report] or [feature request]
* verifying [existing bug reports] and adding [reproduction steps]
* reviewing [pull requests] and testing the changes locally on your machine
* writing or editing [documentation]
* improving test coverage
* fixing a [reproducing bug] or adding a new feature

[bug report]: https://github.com/puma/puma/issues/new?template=bug_report.md
[feature request]: https://github.com/puma/puma/issues/new?template=feature_request.md
[existing bug reports]: https://github.com/puma/puma/issues?q=is%3Aopen+is%3Aissue+label%3Aneeds-repro
[pull requests]: https://github.com/puma/puma/pulls
[documentation]: https://github.com/puma/puma/tree/main/docs

[reproducing bug]: https://github.com/puma/puma/issues?utf8=%E2%9C%93&q=is%3Aopen+is%3Aissue+label%3Abug

Newbies welcome! We would be happy to help you make your first contribution to a F/OSS project.

## Setup

Any questions about contributing may be asked in our [Discussions](https://github.com/puma/puma/discussions).

**If you're nervous, get stuck, need help, or want to know where to start and where you can help**, please don't hesitate to [book 30 minutes with maintainer @nateberkopec here](https://savvycal.com/nateberkopec/puma). He is happy to help!

Nate also [gave a 40 minute conference talk in 2022](https://www.youtube.com/watch?v=w4X_oBuPmTM) detailing how Puma works, a brief overview of its internals, and a quick guide on how to contribute.

#### Clone the repo

Clone the Puma repository:
```sh
git clone git@github.com:puma/puma.git && cd puma
```

#### Ragel

Puma's HTTP parser is generated by [ragel] from the `.rl` files in `ext/puma_http11/`. The generated files, `http11_parser.c` and `org/jruby/puma/Http11Parser.java`, are committed. You need Ragel only if you change a `.rl` file.

macOS:

```sh
brew install ragel
```

Linux:
```sh
apt-get install ragel
```

Windows (Ruby 2.5 and later):
```sh
ridk exec pacman -S mingw-w64-x86_64-openssl mingw-w64-x86_64-ragel
```

After you change a `.rl` file, regenerate both generated files and commit them with your change. Never edit them by hand. The `ragel` CI job regenerates them with Ragel 6.10 on x86-64 Ubuntu 22.04 and fails if the result differs from your commit. Other Ragel versions (Homebrew installs 6.11) and other CPU architectures produce different output, so generate in a matching container:

```sh
docker run --rm --platform linux/amd64 -v "$PWD":/puma -w /puma ubuntu:22.04 sh -c '
  apt-get update -qq && apt-get install -y -qq ragel &&
  ragel ext/puma_http11/http11_parser.rl -C -G2 -I ext/puma_http11 -o ext/puma_http11/http11_parser.c &&
  ragel ext/puma_http11/http11_parser.java.rl -J -G2 -I ext/puma_http11 -o ext/puma_http11/org/jruby/puma/Http11Parser.java'
```

When the `ragel` job fails, it also uploads the files it generated as a workflow artifact.

#### Install Ruby dependencies

Install the Ruby dependencies:
```sh
bundle install
```

#### Compile the native extensions

To run Puma locally, you must compile the native extension. Running the `test` rake task does this automatically, but you may need to manually run the compile command if you want to run Puma and haven't run the tests yet:

Ubuntu, macOS, etc:
```sh
bundle exec rake compile
```

Windows:
```sh
bundle exec rake -rdevkit compile
```

#### Run your local Puma

Now, you should be able to run Puma locally:

```sh
bundle exec bin/puma test/rackup/hello.ru
# -or-
bundle exec ruby -Ilib bin/puma test/rackup/hello.ru
```

Alternatively, you can reference your local copy in a project's `Gemfile`:

```ruby
gem "puma", path: "/path/to/local/puma"
```

See the [Bundler docs](https://bundler.io/man/gemfile.5.html#PATH) for more details.

[ragel]: https://www.colm.net/open-source/ragel/

## Running tests

To run rubocop + tests:

```sh
bundle exec rake
```

To run the test suite only:
```sh
bundle exec rake test
```

Integration tests spawn a Puma process. Unit tests call Puma in-process
(including in-process servers that bind a port). Classification follows the
existing `TestIntegration` helper (see `test/categories.rb`).

To run only the in-process (unit) tests:
```sh
bundle exec rake test:unit
# or
test/runner --unit
```

To run only the process-spawn (integration) tests:
```sh
bundle exec rake test:integration
# or
test/runner --integration
```

To run a single test file:
```sh
bundle exec ruby test/test_binder.rb
```

You can also run tests with [`m`](https://github.com/qrush/m):
```sh
bundle exec m test/test_binder.rb
```

To run a single test:
```sh
bundle exec m test/test_binder.rb:37
```

To run a single test with 5 seconds as the test case timeout:
```sh
TEST_CASE_TIMEOUT=5 bundle exec m test/test_binder.rb:37
```

If you would like more information about extension building, SSL versions, your local Ruby version, and more, use the PUMA_TEST_DEBUG env variable:

```sh
PUMA_TEST_DEBUG=1 bundle exec rake test
```

Puma also has a helper file for running tests, see the comments at the top of the `test/runner` file.  Example:
```
test/runner -v test_puma_server.rb
```

#### Local CI

`test/local-ci` runs the Linux jobs from `.github/workflows/tests.yml` in Docker, on the same Ruby builds that CI uses. It needs Ruby, git, and Docker. Uncommitted changes are included.

```sh
test/local-ci                       # quick set: 3.0, newest, head, jruby, truffleruby
test/local-ci --all                 # every Linux CI job
test/local-ci --base main           # report only failures that are new compared to main
test/local-ci --only 3.0,jruby -- test_puma_server
test/local-ci --only jruby --repeat 20 -- test_integration_cluster
test/local-ci --list                # show Linux CI jobs; * marks the selected ones
```

With `--base`, each new failure is rerun on both commits and labeled `REGRESSION`, `flaky`, `also fails on base`, or `passes on rerun`. macOS and Windows jobs are not run.

#### File limits

Puma's test suite opens up a lot of sockets. This may exceed the default limit of your operating system. If your file limits are low, you may experience "too many open files" errors when running the Puma test suite.

```
# check your file limit
ulimit -S -n

# change file limit for the current session
ulimit -S -n <value>
```

We find that values of 4000 or more work well. [Learn more about your file limits and how to change them here.](https://wilsonmar.github.io/maximum-limits/)

## How to contribute

Puma could use your help in several areas!

**Don't worry about "claiming an issue". No issues are "claimed" in Puma.** Just start working on it. The issue tracker is almost always kept updated, so if there is an open issue, it is ready for you to contribute (unless you have questions about how to close the issue - then please ask!). Once you have a few lines of code, post a draft PR. We are more than happy to help once you have a draft PR up.

**Do check for an existing pull request first.** We can merge only one fix per issue, and several issues have each drawn three or four competing PRs. See [Before you write code](#before-you-write-code).

**New to systems programming? That's ok!** Puma deals with concepts you may not have been familiar with before, like sockets, TCP, UDP, SSL, and Threads. That's ok! You can learn by contributing. Also, see the "Bibliography" section at the end of this document.

**The [contrib-wanted] label indicates that an issue might be approachable to first-time contributors.**

**Reproducing bug reports**: The [needs-repro] label indicates that an issue lacks reproduction steps. You can help by reproducing the issue and sharing the steps you took in the comments.

**Helping with our native extensions**: If you are interested in writing C or Java, we could really use your help. Check out the issue labels for [c-ext] and [JRuby].

**Fixing bugs**: Issues with the [bug] label have working reproduction steps, which you can use to write a test and submit a patch.

**Writing features**: The [feature] label highlights requests for new functionality. Write tests and code up our new feature!

**Code review**: Take a look at open pull requests and offer your feedback. Code review is not just for maintainers. We need your help and eyeballs!

**Write documentation**: Puma needs more docs in many areas, especially where we have open issues with the [docs] label.

## Reproduction steps

Reproducing a bug helps identify the root cause of that bug so it can be fixed.

To get started, create a rackup file and config file and then run your test app
with:
```sh
bundle exec puma -C <path/to/config.rb> <path/to/rackup.ru>
```

For example, using a test rack app ([`test/rackup/hello.ru`][rackup]) and a
test config file ([`test/config/settings.rb`][config]):
```sh
bundle exec puma -C test/config/settings.rb test/rackup/hello.ru
```

There is also a Dockerfile available for reproducing Linux-specific issues:
```sh
docker build -f tools/Dockerfile -t puma .
docker run -p 9292:9292 -it puma
```

[rackup]: https://github.com/puma/puma/blob/main/test/rackup/hello.ru
[config]: https://github.com/puma/puma/blob/main/test/config/settings.rb

## Pull requests

Maintainers review in their free time, so make your pull request quick to review. The points below are what reviewers most often ask contributors to change.

### Before you write code

* **Look for earlier work.** Search issues and pull requests, open and closed, for the issue number and for the method, option or error message involved. Read the whole issue: a maintainer may already have decided how to fix it, or decided against it. If an open PR already covers the problem, test or review that one. Open a second PR only when it does something the first does not, and say what that is.
* **Check that the bug still exists.** Reproduce it on `main`, not only on the release you run.
* **Agree on new behavior first.** A new option, hook or public method, or a change to default behavior, needs a maintainer to agree with the design. Describe the interface in the issue or in a draft PR before you build all of it.
* **Send one pull request at a time.** Review comments on your first PR usually apply to your next ones too.

### Keep it small

* One change per PR, and aim for 100 changed lines or fewer. Refactoring, renames and unrelated fixes go in their own PRs. If a reviewer could judge two parts separately, send them separately.
* Prefer the smallest fix. Change the existing condition before you add a second one, and leave the arguments of existing hooks and callbacks as they are.
* Keep what the old code handled. When you rewrite a method, check each case it covered, such as letter case, whitespace, `nil` and IPv6 addresses, and add a test for the ones your change touches.
* Keep the public API small. Puma's public API is its configuration and its HTTP behavior ([versioning policy](docs/puma_support.md#versioning)), and each addition has to be supported for years. Add the fewest options and arguments that solve the problem. Classes such as `Puma::Server` and `Puma::Client` are internal, so don't add methods to them, or to the `Puma` module, for apps to call. A per-request feature goes in the Rack env under a `puma.` key, like `env["puma.mark_as_io_bound"]`.
* Say so in the description when a change can break an existing app or config. Breaking changes wait for a major release.
* The HTTP parser and the TLS code exist twice, in C and in Java, both under `ext/puma_http11/`. Change both.
* Puma runs on Ruby 3.0 and later, JRuby, TruffleRuby and Windows ([support policy](docs/puma_support.md)). Use only syntax and methods that Ruby 3.0 has. JRuby and Windows have no `fork`, and Windows lacks most signals.

### HTTP behavior

Puma follows RFC 9110 and RFC 9112, and a deviation from them is a bug. When you change how Puma parses a request or writes a response, cite the RFC section in the description and test the forms the RFC allows: for example, connection options are case-insensitive, and list items may have whitespace around the commas.

### Tests

Code contributions should generally include test coverage. If you aren't sure how to
test your changes, please open a pull request and leave a comment asking for
help.

* **A new test must fail on `main`.** Reviewers run your tests without your fix. A test that passes there proves nothing.
* **Synchronize, don't sleep.** To wait for another thread or process, use a `Queue`, an `IO.pipe`, or the `wait_for_server_to_*` helpers in `test/helpers/integration.rb`. CI retries a failing test up to three times, so a test that depends on timing can pass in your PR and then fail in everyone else's.
* **Run the test on its own**, for example `bundle exec ruby test/test_binder.rb -n /pattern/`. The full suite loads files that a single test file may forget to require.
* **Use the helpers.** Tests subclass `PumaTest`. `test/helpers/test_puma/puma_socket.rb` has client sockets (`send_http`, `send_http_read_response`) that are closed for you. `skip_unless :fork` and `skip_if :jruby, :windows` handle platforms that lack a feature.

### Performance changes

A performance PR needs numbers. Show several runs of `main` and of your branch, with the command you used, so that a reviewer can repeat them and can tell the gain from run-to-run noise. Cover more than one thread and worker count, a CPU-bound app such as `test/rackup/sleep_fibonacci.ru`, and connections that sit idle on keep-alive. A load generator that keeps every connection busy hides the cost of a change to accept or keep-alive handling. `benchmarks/local/` has scripts for `wrk` and `hey`.

### Comments and documentation

Write code and tests that need no comment to explain them. Reviewers regularly ask for comments that restate a method name or a test name to be removed. Keep a comment that says what the code cannot, such as where a constant's value came from.

Document a new config option in `lib/puma/dsl.rb`: what it does, its default, and one example. Keep other docs short, and link to the README or the DSL docs instead of repeating them.

There's no need to update the changelog ([`History.md`](History.md)); that is done [when a new release is made](Release.md).

### Opening the pull request

Please open draft PRs as soon as you are ready for feedback from the community. The test jobs do not run on draft PRs, so mark the PR ready for review when you want CI, and put it back in draft while you rework it.

In the description, state the problem, what you changed, why you chose this approach, and how you verified it: the commands you ran and what they printed.

Puma uses [GitHub Actions](https://docs.github.com/en/actions) for CI testing. Please consider running the workflows in your fork before creating a PR. It is possible to enable GitHub Actions on your fork in the repository's `Actions` tab.

When reporting bugs or reproducing issues, please use the latest patch release of your Ruby minor version, as described in the [Ruby version support policy](docs/puma_support.md#ruby-version-support-policy).

### After you open it

A red CI job is yours until you show otherwise. Run the failing test on `main`: `test/local-ci --base main` does this for the Linux jobs and labels each failure as a regression, flaky, or also failing on `main`. If the failure is not from your change, say which test failed and link the run on `main` that fails the same way. Contributors cannot re-run jobs, so ask a maintainer.

Rebase on `main` when a maintainer asks, or when the fix for a failing job has landed there.

If changes are suggested, and you agree with them, please use a separate commit
for them.  We can always squash commits when merging.

### AI-assisted contributions

Contributions written with AI tools are welcome, and the maintainers use them too. The same standards apply, plus these:

* Start the description with `_This is AI-assisted. Model: <model>_`.
* Run the code before you open the PR. On a machine with no Ruby, build `tools/Dockerfile`, which needs only Docker, or run CI on your fork.
* Read the whole diff yourself, and answer review questions about it yourself.

Coding agents should start with [`AGENTS.md`](AGENTS.md).

## Pull requests - bug fixes

If your PR is a 'bug fix', please consider having it be at least two commits.

The first commit(s) should be the tests, which should fail when run on main.
The second set of commits (maybe a single one) should be the fixes.

This allows maintainers to check out the tests commit and run them, verifying that
the bug exists.

## Backports

Puma does not have a backport "policy" - maintainers will not consistently backport bugfixes to previous minor or major versions (we do treat security differently, see [`SECURITY.md`](SECURITY.md)).

For Ruby patch-level bugs, we may add targeted workarounds. When we do, we keep those workarounds in place for the lifetime of the affected Ruby minor series, even if a later patch release fixes the underlying issue.

As a contributor, you may make pull requests against `-stable` branches to backport fixes, and maintainers will release them once they're merged. For example, if you'd like to make a backport for 4.3.x, you can make a pull request against `4-3-stable`. If there is no appropriate branch for the release you'd like to backport against, please just open an issue and we'll make one for you.

## Bibliography/Reading

Puma can be a bit intimidating for your first contribution because there are a lot of concepts here that you've probably never had to think about before - Rack, sockets, forking, threads etc. Here are some helpful links for learning more about things related to Puma:

* [Puma's Architecture docs](https://github.com/puma/puma/blob/main/docs/architecture.md)
* [The Rack specification](https://github.com/rack/rack/blob/main/SPEC.rdoc)
* [Working with...](https://workingwithruby.com/) "Working With" is an excellent (and now free) Ruby book series about working with Threads, TCP and Unix Sockets.
* The Ruby docs for IO.pipe, TCPServer/Socket.
* [nio4r documentation](https://github.com/socketry/nio4r/wiki/Getting-Started)
